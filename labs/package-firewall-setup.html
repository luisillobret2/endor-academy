1

Meet the Attack

Challenge scenario: It is 4:45 p.m. on a Friday. Alice on the payments team types pip install reqeusts — one transposed letter. Without a firewall, that package installs, its setup.py runs, and a second-stage payload quietly exfiltrates the AWS credentials in her environment. Your mission: make sure that typo never becomes an incident.

The Endor Labs Package Firewall blocks malicious packages at install time, covering three supply-chain patterns:

  • Typosquatting — packages named to mimic popular ones and catch install typos
  • Dependency confusion — public packages published under your internal package names
  • Compromised packages — legitimate packages taken over or updated with malicious code

First, inspect the typosquat's registry metadata — but never install it:

# Inspect the typosquat on the public registry (DO NOT install) pip index versions reqeusts
$ pip index versions reqeusts reqeusts (2.25.1) Available versions: 2.25.1, 2.24.0 Published 2 days ago by user4821 (account age: 5 days) Description: "A fork of requests with bug fixes" 3 downloads this week — the real "requests" has millions
Notice Never install a suspicious package "just to look" — setup.py executes during installation. Registry metadata only. Everything below is safe because the firewall does the handling.

  • ✓ Inspected (but did not install) the typosquat's metadata

Enable the Firewall in Monitor Mode

In the Endor Labs dashboard, open Policies → Package policies and enable the Package Firewall for your organization. Start in Monitor mode: every install decision gets logged, but nothing is blocked yet. This lets you tune rules against real traffic before you enforce.

Then point your package managers at the firewall's proxy endpoints so installs flow through Endor Labs:

# Route installs through the Endor Labs Package Firewall (training values) pip config set global.index-url https://proxy.endorlabs.com/acme-financial/pypi/simple # npm equivalent npm config set registry https://proxy.endorlabs.com/acme-financial/npm/
$ pip config set global.index-url https://proxy.endorlabs.com/acme-financial/pypi/simple global.index-url set to https://proxy.endorlabs.com/acme-financial/pypi/simple $ pip install requests Collecting requests Downloading requests-2.31.0 from https://proxy.endorlabs.com/acme-financial/pypi/simple [monitor] Package Firewall would have ALLOWED requests 2.31.0 (rule: allow-known-good) Successfully installed requests-2.31.0
Tip Monitor mode shows the decision the firewall would make on every install. The exact proxy URLs and registry setup steps (npm, PyPI, and private registries) live at docs.endorlabs.com.
  • ✓ Enabled the Package Firewall in Monitor mode
  • ✓ Pointed pip and npm at the firewall proxy
  • ✓ Observed a monitor-mode decision in the install output
3

Author the Policy Rules

Back in Policies → Package policies → Add rule, create the ruleset below. Rules evaluate in order and the first match wins. This is the heart of the challenge — a ruleset that blocks the bad, allows the good, and never breaks a build unnecessarily.

# Package Firewall ruleset (first match wins) 1. block-typosquats name closely mimics a top-500 package -> BLOCK 2. block-dependency-confusion internal namespace acme-* resolved from a public registry -> BLOCK 3. block-malware malware verdict: malicious (always on) -> BLOCK 4. allow-known-good Endor Score security >= 8.0 and activity score >= 7.0 -> ALLOW 5. default everything else -> ALLOW + log

Rationale for each rule:

  • block-typosquats — catches reqeusts, requeats, and friends before Alice's typo resolves
  • block-dependency-confusion — anything named acme-* must come from your private index; public lookups are attacks until proven otherwise
  • block-malware — Endor Labs malware detection runs on every package automatically; known-malicious code never passes
  • allow-known-good — packages with strong Endor Scores (activity, popularity, security, code quality) flow freely, so developers never feel the firewall
  • default allow + log — while policies are new, unknowns are logged, not blocked; tighten this once you trust the ruleset
  • ✓ Created the typosquat rule
  • ✓ Created the dependency-confusion rule for the acme-* namespace
  • ✓ Left a permissive default with logging while the ruleset is new

Watch the Typosquat Get Blocked

Flip the firewall from Monitor to Enforce. Now replay Alice's Friday typo and watch what happens instead of an incident:

$ pip install reqeusts ERROR: Package blocked by Endor Labs Package Firewall Package: reqeusts 2.25.1 Reason: typosquat of popular package "requests" (name similarity 0.92) Verdict: MALICIOUS — setup.py fetches a second-stage payload Policy: block-typosquats (rule tq-01) Audit ID: fw-2026-1104-8f3a The package was NOT installed. If you believe this is a false positive, share audit ID fw-2026-1104-8f3a with #appsec.

The package never reached the virtual environment, the lockfile, the CI runner, or production. Alice gets a clear error naming the rule, the reason, and a false-positive path — and the correct package still works:

$ pip install requests Collecting requests [endor firewall] allowed by rule allow-known-good (Endor Score: 9.1) Successfully installed requests-2.31.0
Why this works The block happens at install time — the earliest possible moment. Blocking after CI, or worse after deployment, means the malicious code already ran.
  • ✓ Switched the firewall to Enforce mode
  • ✓ Observed the typosquat blocked with reason, policy, and audit ID
  • ✓ Confirmed the legitimate requests package still installs cleanly

Dependency Confusion, Blocked

The second attack pattern: an adversary publishes acme-utils to public PyPI, betting that your build resolves the public package whenever the internal one is missing. Your block-dependency-confusion rule makes that bet lose:

$ pip install acme-utils ERROR: Package blocked by Endor Labs Package Firewall Package: acme-utils 0.0.1 (public PyPI) Reason: dependency confusion — "acme-*" is an internal namespace Policy: block-dependency-confusion (rule dc-03) Hint: install from the Acme private index instead Audit ID: fw-2026-1104-90b2

Note the hint: the firewall distinguishes between where the package came from and who owns the name. Internal names must resolve from internal indexes — always.

Notice Dependency confusion has breached real companies: if any resolver checks the public registry first, the attacker's package — with the same name as yours but malicious content — wins the race. The namespace rule closes the door at install time.
  • ✓ Saw the internal-namespace rule block a public acme-utils package
  • ✓ Noted the remediation hint pointing to the private index

Audit Trail and CI

In the dashboard, open the Package Firewall audit log. Every allow and block is recorded with the user, machine, package, version, verdict, matched policy, and audit ID. Search for fw-2026-1104-8f3a — you should find Alice's typo attempt (yours, in this lab), the verdict, and the rule that stopped it.

Route block alerts to Settings → Notifications → #appsec so the team sees blocks in real time, then wire the same proxy endpoints into CI so the firewall covers the pipeline too:

# CI environment (example: GitHub Actions) — same firewall, same rules env: PIP_INDEX_URL: https://proxy.endorlabs.com/acme-financial/pypi/simple NPM_CONFIG_REGISTRY: https://proxy.endorlabs.com/acme-financial/npm/
Challenge wrap-up One mis-typed package name used to be an incident report. Now it is a one-line block message, an audit entry, and a Slack ping — and Alice installs the right package on her second try. That is the Package Firewall doing your job before it becomes your job.

🧠 Knowledge Check

What is typosquatting?
  • Squatting on a dormant maintainer's account
  • Publishing a package whose name closely mimics a popular package to catch install typos
  • Reusing a GPL library in a commercial product
  • Registering a package name and selling it to the highest bidder
Why should you enable Monitor mode before Enforce?
  • Monitor mode blocks more packages
  • Enforce mode requires a paid plan
  • To observe would-be decisions on real traffic and tune rules without breaking installs
  • Monitor mode scans containers faster
How does a dependency confusion attack succeed?
  • By typo-squatting the most-downloaded packages
  • By compromising a maintainer's publishing credentials
  • Your resolver fetches an attacker's public package that shares a name with an internal package
  • By downgrading a transitive dependency in a lockfile
With the firewall enforcing, what happens when a developer runs pip install reqeusts?
  • The package installs, then a scan flags it hours later
  • The install fails immediately at the firewall — the package never reaches the venv, lockfile, or CI
  • The install succeeds but the package is quarantined in the venv
  • The developer receives a survey about typing accuracy
