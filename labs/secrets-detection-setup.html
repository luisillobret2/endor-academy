Secrets Detection Setup

Guided
🕓 45 min 🏆 100 XP 🔄 Secrets 📚 5 steps

🎯 Lab Objectives

  • Enable Endor Labs secrets detection for a project — one policy from laptop to pipeline
  • Catch a secret before it is committed
  • Write a custom rule for an internal token format
  • Run a historical scan of git history for leaked credentials
  • Route detection alerts to Slack, email, and Jira
  • Remediate detected secrets: rotate first, then clean git history
1

Enable Secrets Detection

Endor Labs secrets detection runs on the same policy from a developer laptop to the pipeline: what gets flagged locally is exactly what fails the CI build. Turn it on for the project, and set it as the organization default so every new project inherits it.

In the Endor Labs dashboard, open Projects → checkout-service → Scan settings and enable Secrets detection. Then, under Settings → Policies, mark it as the default for new projects.

Verify locally with a targeted scan of the working tree and staged changes:

# Scan the current working tree and staged changes for secrets endorctl scan --secrets
$ endorctl scan --secrets Scanning working tree and staged changes for secrets... Built-in rules loaded: 78 (AWS, GCP, Azure, GitHub, Stripe, Slack, private keys, ...) DETECTED critical AWS Access Key ID File: src/main/resources/application.properties Line: 12 Match: AKIA************************************ 1 secret found in the working tree. Scan before you commit — a secret in git history is exposed forever.
Tip Because the same policy governs laptop and pipeline, there is no rule drift between developer machines and CI. Flag names and behavior evolve — the latest flag syntax lives at docs.endorlabs.com.
  • ✓ Enabled secrets detection for checkout-service and set it as the org default
  • ✓ Ran endorctl scan --secrets locally and found the staged AWS key
  • ✓ Removed the key from application.properties before committing
2

Write a Custom Rule for Internal Token Formats

Built-in rules cover well-known providers. They cannot know that Acme's internal IAM issues tokens matching acme_ followed by 32 alphanumeric characters — that is what custom rules are for.

In the dashboard, open Policies → Finding policies → Add custom secret rule and define:

# Custom secret rule (defined in the dashboard, applied everywhere) name: Acme internal IAM token description: Tokens issued by Acme internal IAM (prefix acme_) pattern: 'acme_[a-zA-Z0-9]{32}' severity: critical

Save it, then re-run the local scan to confirm the new rule catches the seeded internal token:

$ endorctl scan --secrets Scanning working tree and staged changes... Rules loaded: 78 built-in, 1 custom DETECTED critical Acme internal IAM token (custom rule) File: scripts/seed-dev-data.py Line: 18 Match: acme_********************************
Notice Test new patterns against a sample of your real code before enabling them org-wide. An overly broad regex generates false positives, and false positives train developers to ignore alerts — the one outcome you cannot afford.
  • ✓ Created the acme_ custom rule with critical severity
  • ✓ Verified the rule fires on the seeded token in seed-dev-data.py
3

Run a Historical Scan

Secrets detection is not only for new commits. A historical scan examines git history to surface credentials that were committed months ago and forgotten — the classic "it was deleted in a later commit" exposure.

Run it from the CLI with a depth of 500 commits (the dashboard equivalent is Projects → Scans → Run scan → include git history):

# Scan git history for leaked secrets, 500 commits deep endorctl scan --secrets --historical --depth 500 --output json > secrets-history.json
$ endorctl scan --secrets --historical --depth 500 --output json > secrets-history.json Starting historical scan... Repository: checkout-service Scanning 500 commits... commit a3f1c2d (2023-06-14) SECRET FOUND: AWS Access Key ID (critical) File: src/main/resources/config.properties Line 12 Match: AKIAIOSFODNN7* commit 8b9e021 (2023-08-02) SECRET FOUND: GitHub Personal Access Token (critical) File: .github/workflows/deploy.yml Line 27 Match: ghp_* Historical scan complete. Critical: 2 secrets found Total: 2 secrets across 2 commits Findings exported to secrets-history.json
Notice The current branch no longer contains these files — but the commits still do. Anyone who ever cloned the repository has these credentials. Treat them as compromised, regardless of when they were leaked.
  • ✓ Ran the historical scan across 500 commits
  • ✓ Reviewed both detected secrets and their commit locations
  • ✓ Exported findings to secrets-history.json
4

Route the Alerts

A secret found at 2 a.m. is better handled then than in next year's audit. Configure detection routing in the dashboard under Settings → Notifications:

  • Slack: post critical and high secrets to #security-alerts — a channel humans watch around the clock
  • Email: page the on-call address for critical detections
  • Jira: auto-create an incident ticket in project SEC for every critical secret, so remediation status is tracked end to end

Use Send test alert to verify the full route. Within seconds you should see:

# Slack #security-alerts, seconds after Send test alert: [Endor Labs] Test notification from Acme Financial Routing: slack:#security-alerts email:oncall@acme.example jira:SEC Event type: secret detected (critical) — armed
Tip Route secrets to multiple channels simultaneously: Slack for speed, email for paging, Jira for accountability. A secret with a ticket number does not get "handled later."
  • ✓ Configured Slack routing for critical and high secrets
  • ✓ Set the on-call email for critical detections
  • ✓ Enabled Jira incident creation in project SEC and received the test alert
5

Remediate: Rotate First, Then Clean History

Follow the incident response order for each detected secret — the order matters:

  1. Rotate the credential in the provider console (for the AWS key: AWS IAM — deactivate the old key, issue a new one)
  2. Remove the secret from git history with git filter-repo
  3. Force-push the rewritten history and have the team re-clone
  4. Re-scan to verify remediation
# 1. Rotate in the provider console first (AWS IAM) — then: pip install git-filter-repo git filter-repo --replace-text <(echo "AKIAIOSFODNN7EXAMPLE==>REDACTED") # 2. Force-push the cleaned history git push origin --force --all # 3. Verify the fix endorctl scan --secrets --historical --depth 500
$ git filter-repo --replace-text <(echo "AKIAIOSFODNN7EXAMPLE==>REDACTED") Parsing commits... Rewriting history... Replaced 1 occurrence in 1 commit. Reflog and origin remotes removed. $ git push origin --force --all Enumerating objects: 487, done. Force-pushed rewritten history to origin. $ endorctl scan --secrets --historical --depth 500 Re-scanning git history... Scan complete. 0 secrets found. Remediation verified.
Notice Rotating is mandatory and first. Cleaning git history does not undo the exposure — anyone who cloned before the rewrite still has the original credential. Rotate first, then clean, then re-scan.
  • ✓ Rotated both compromised credentials in their provider consoles
  • ✓ Removed the secrets from git history and force-pushed
  • ✓ Re-scanned and confirmed 0 secrets remaining

What is the correct first action when a secret is detected in git history?
  • Remove the secret from git history immediately
  • Rotate the compromised credential in the provider console
  • Delete the repository and recreate it
  • Wait for the next scan to confirm the finding
Why does a historical scan matter if the secret was already deleted from the current branch?
  • It does not — deleted files are gone
  • It is only needed for compliance paperwork
  • The commits still contain the secret, and anyone who cloned the repo has it
  • It speeds up future scans
Why create a custom rule like the acme_ pattern?
  • Built-in rules slow down scans
  • Built-in rules cover known providers but cannot know your organization's internal token formats
  • Custom rules are required to enable secrets detection
  • Custom rules bypass severity policies
Which remediation sequence is correct?
  • Clean git history → rotate → re-scan
  • Re-scan → rotate → clean git history
  • Rotate → clean git history → force-push → re-scan
