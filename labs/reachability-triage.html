Reachability Triage

Guided
🕓 45 min 🏆 100 XP 🔄 Reachability 📚 6 steps

🎯 Lab Objectives

  • Survey a raw findings backlog and split it by reachability
  • Read function-level call paths to confirm true exploitability
  • Dismiss unreachable findings with documented, auditable reasons
  • Resolve findings whose reachability is Unknown
  • Prioritize the remaining work by real risk, not raw CVE counts
  • Set policies and alerts so the backlog stays clean
1

Survey the Backlog

You are the new AppSec engineer for Acme Financial's checkout-service. The service has 214 open findings — the previous tool alerted on every CVE in the tree, and nobody has touched the backlog in months. Your job is to find the handful that can actually be exploited.

In the Endor Labs dashboard, open the findings view for checkout-service and add the Reachability filter. The backlog splits immediately:

# Triage board — reachability split of 214 findings Reachable 6 e.g. CVE-2021-44228 (log4j-core, critical) Unreachable 187 e.g. CVE-2022-22965 (spring-webmvc, critical) Unknown 21 e.g. CVE-2020-36518 (jackson-databind, high)

For offline analysis, export the current findings as JSON:

$ endorctl scan --output json > findings.json Scanning project: checkout-service Resolving dependencies... done Analyzing reachability... done 214 findings exported to findings.json 6 reachable / 187 unreachable / 21 unknown
Notice Only 6 of 214 findings can actually be executed through your code. That ratio — not the raw count — is what reachability analysis gives you. Most of this backlog is noise, and you are about to dismiss it properly.
  • ✓ Opened the findings view filtered by reachability
  • ✓ Confirmed the 6 / 187 / 21 reachability split
  • ✓ Exported findings to findings.json
2

Confirm the Reachable Criticals

Open the CVE-2021-44228 finding (Log4Shell, log4j-core 2.14.1). Expand the Call path section and read it frame by frame:

# Call path — CVE-2021-44228 (critical 10.0, REACHABLE) Entry point: POST /api/orders (internet-facing) 1. OrderController.createOrder() [your code] 2. OrderService.validatePayment() [your code] 3. Logger.error(paymentCtx) [log4j-api 2.14.1] 4. JndiLookup.lookup() [log4j-core 2.14.1] * vulnerable function

Attacker-controlled order data flows from an internet-facing endpoint into a log call that triggers the vulnerable JNDI lookup. This is a confirmed, exploitable path — it is your P1.

The second reachable critical, CVE-2022-1471 in snakeyaml, has its own path through the config loader that calls Yaml.load() on a developer-editable file. For each finding, note the remediation options Endor Labs presents: the direct upgrade (log4j-core 2.17.1), an Endor Patch backport if you cannot take the full upgrade, or a documented, time-boxed exception.

Tip Reachability is function-level, not package-level: log4j-core being present is not the problem — a specific function being called by your specific code is. That is why two criticals in the same package tree can have completely different verdicts.
  • ✓ Traced the Log4Shell call path end to end
  • ✓ Confirmed the snakeyaml finding's path through the config loader
  • ✓ Noted the remediation options for each reachable critical
3

Dismiss the Unreachable Noise — Properly

Open CVE-2022-22965 (Spring4Shell, spring-webmvc 5.3.16). The call path section states why it is unreachable: no path from application code reaches the vulnerable data-binding code — the service is not deployed as a WAR on a standalone Tomcat, and no request parameter binds to a class property.

Dismiss it: click Dismiss, choose the reason Unreachable — no call path from application code, and set an expiry of 90 days. The dismissal is recorded as an auditable exception linked to the finding and the dependency version.

Now select all remaining unreachable findings in the list (the filter already isolates them), and apply the same dismissal with the same reason and expiry as a bulk action.

# Dismissal applied to 187 unreachable findings Reason: Unreachable — no call path from application code Expiry: 90 days (auto re-opens if reachability changes) Recorded: learner@endorlabs.com, 2026-11-04T14:22Z Scope: 187 findings across 62 packages
Notice Never mass-dismiss without a reason and an expiry. The expiry matters: if a future commit adds a call path to one of these functions, the finding re-opens automatically. Dismissal is a documented bet that reachability will not change — not a delete button.
  • ✓ Dismissed CVE-2022-22965 with a documented reason and 90-day expiry
  • ✓ Bulk-dismissed the remaining unreachable findings with the same policy
  • ✓ Verified each dismissal is visible as an auditable exception
4

Resolve the Unknowns

21 findings have Unknown reachability. Typical cause: the analysis could not confirm which version of a dependency actually ships at runtime, so it cannot decide whether the vulnerable function is called. Example: CVE-2020-36518 in jackson-databind — two build profiles pin different versions.

Confirm the pinned version, align the build, and re-scan:

$ endorctl deps | grep jackson com.fasterxml.jackson.core:jackson-databind:2.13.2 (pinned in pom.xml) $ endorctl scan Scanning project: checkout-service Resolving dependencies... done Analyzing reachability... done CVE-2020-36518 (jackson-databind 2.13.2): unknown -> unreachable 20 remaining unknown findings queued for version confirmation
Tip For internet-facing services, treat Unknown as if it were Reachable until proven otherwise. Verify the runtime version the same day; never let an unknown sit quietly on a critical finding.
  • ✓ Confirmed the pinned jackson-databind version with endorctl deps
  • ✓ Re-scanned and watched the Unknown status resolve to Unreachable
  • ✓ Scheduled version confirmation for the remaining unknowns
5

Prioritize the Survivors

Your real backlog is now 6 reachable findings plus a few unknowns worth verifying. Rank by reachability first, then severity, then exposure — checkout-service is an internet-facing payment path, which raises the stakes on everything reachable in it.

# Final triage board — checkout-service P1 CVE-2021-44228 log4j-core 2.14.1 critical reachable fix today P1 CVE-2022-1471 snakeyaml 1.29 critical reachable fix today P2 CVE-2022-42003 jackson-databind 2.13.2 high reachable this sprint P2 CVE-2023-24998 commons-fileupload 1.4 high reachable this sprint P3 20 unknown-reachability findings verify versions this week Snoozed 187 unreachable findings (auto-expire in 90 days)
Proof the workflow pays Zebra cut SCA noise by 97% using exactly this reachability-first triage. A 214-item backlog became 6 actionable findings — small enough to actually finish, and each with a call path that proves why it matters.
  • ✓ Ranked the reachable findings into a fix queue (P1/P2/P3)
  • ✓ Recorded what happens to snoozed findings when their expiry passes
6

Make the Triage Stick

Triage is not a one-time cleanup — configure the platform so the backlog stays clean. In the dashboard:

  • Policies → Finding policies: require a reason and an expiry on every dismissal, so silent mass-dismissals are impossible by construction.
  • Settings → Notifications: post to #appsec the moment a new reachable critical appears — the event worth interrupting a human for.

Then fix the P1s (the endorctl-first-scan lab shows the upgrade loop) and re-scan:

$ endorctl scan Scanning project: checkout-service Analyzing reachability... done Findings summary Critical: 2 (0 reachable) — P1 fixes merged, PR in review High: 7 (2 reachable) — scheduled this sprint New reachable criticals: 0 Notification policy rp-07 armed: alert #appsec on new reachable critical Scan finished in 2m 08s
The platform journey This lab is the Day 1 "prioritize" step of the Endor Labs workflow — Scan, Triage, Remediate. Day 0 was onboarding; from Day 2 on, you optimize: automating PRs, tuning policies, and letting agents help with the routine fixes.

  • ✓ Confirmed dismissal exceptions require a reason and an expiry
  • ✓ Re-ran the scan and verified the reachable criticals were resolved

🧠 Knowledge Check

What makes a finding Reachable?
  • The vulnerable package is a direct dependency
  • A complete call path exists from your code to the vulnerable function
  • The CVE has a CVSS score of 9.0 or higher
  • The package appears in the SBOM
By how much did Zebra cut SCA noise using reachability?
  • 50%
  • 75%
  • 97%
  • 100%
What is the correct way to dismiss an unreachable finding?
  • Delete it from the findings list permanently
  • Ignore it — it will disappear from the backlog eventually
  • Dismiss with a documented reason and an expiry, so it re-opens if reachability changes
  • Mark it as fixed and close the ticket
A critical finding in an internet-facing service has Unknown reachability. What should you do?
  • Dismiss it as unreachable and move on
  • Wait for the next weekly scan to re-evaluate it
  • Treat it as reachable until you verify the runtime version and resolve the status
  • Escalate to the CTO immediately regardless of context
