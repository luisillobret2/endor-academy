GitHub Actions Integration

Guided
🕓 60 min 🏆 100 XP 🔄 Integration 📚 6 steps

🎯 Lab Objectives

  • Connect a repository with the Endor Labs GitHub App
  • Authenticate CI scans keylessly with GitHub OIDC — no stored tokens
  • Create a GitHub Actions workflow that runs endorctl scan
  • Trigger a pull request and review the automated PR scan comment
  • Configure policy-driven fail conditions and branch protection
  • Add a nightly full scan to keep the baseline fresh
1

Connect the Repository with the Endor Labs GitHub App

In the Endor Labs dashboard, open Settings → Integrations → GitHub and install the Endor Labs GitHub App on your organization, granting it access to checkout-service. This is the piece that enables monitoring, PR comments, and automated upgrade PRs.

Then clone the repository so you can add the workflow:

# Clone the repository gh repo clone acme-financial/checkout-service cd checkout-service
$ gh repo clone acme-financial/checkout-service Cloning into 'checkout-service'... Repository connected via Endor Labs GitHub App (2 projects synced)
Why the app matters PR scan comments post as the Endor Labs integration — you will not manage a bot account or store a GitHub PAT in your secrets. The workflow you create next only needs to run the scan; the app handles the GitHub-facing feedback.
  • ✓ Installed the Endor Labs GitHub App with access to the repository
  • ✓ Cloned checkout-service locally
2

Authorize the Runner: Keyless OIDC First

Every CI integration has the same weak point: the credential stored in the pipeline. Endor Labs removes it. GitHub Actions runners can mint short-lived OIDC tokens, and Endor Labs trusts your organization's GitHub identity — so endorctl authenticates with no stored secret: nothing to leak, nothing to rotate.

Enable keyless auth in the dashboard: Settings → Integrations → GitHub → Keyless (OIDC). Then confirm the workflow only needs the standard OIDC permission:

# The only permission keyless auth needs permissions: contents: read id-token: write # required for keyless OIDC
$ gh secret list (no repository secrets — the workflow authenticates keylessly via GitHub OIDC)
Fallback: ENDOR_TOKEN Runners that cannot mint OIDC tokens (some self-hosted setups) can use an API key instead: create one in Settings → API keys, store it as the GitHub secret ENDOR_TOKEN, and export it in the step. Keyless is the default; the token is the exception.
  • ✓ Enabled keyless OIDC auth for GitHub in the dashboard
  • ✓ Confirmed no long-lived token secret is needed
3

Create the Workflow

Create .github/workflows/endor-scan.yml. The workflow installs endorctl, runs the scan with SARIF output, and uploads the results to GitHub code scanning:

# .github/workflows/endor-scan.yml name: Endor Labs Scan on: pull_request: branches: [main] push: branches: [main] jobs: endor-scan: runs-on: ubuntu-latest permissions: contents: read id-token: write steps: - name: Checkout code uses: actions/checkout@v4 - name: Install endorctl run: curl -fsSL https://endorlabs.com/install.sh | bash - name: Run Endor Labs scan run: endorctl scan --output sarif - name: Upload SARIF to code scanning if: always() uses: github/codeql-action/upload-sarif@v3 with: sarif_file: endor.sarif
Machine-readable output endorctl scan --output sarif writes endor.sarif for code scanning; --output json is the choice when you want raw results stashed as a workflow artifact. The current workflow syntax lives at docs.endorlabs.com.
  • ✓ Created .github/workflows/endor-scan.yml
  • ✓ Included id-token: write for keyless auth
  • ✓ Added the SARIF upload step for code scanning

Trigger a PR and Watch the Loop

Push a branch with a small change and open a pull request — the event the workflow is built around:

# Create a branch, a small change, and a PR git checkout -b feature/add-config echo "LOG_LEVEL=info" >> .env.example git add .env.example git commit -m "feat: add log level config" git push origin feature/add-config gh pr create --fill
$ gh pr create --fill https://github.com/acme-financial/checkout-service/pull/58 $ gh run watch --exit-status Job: endor-scan Checkout code ................. done Install endorctl .............. done Run Endor Labs scan ........... done Authenticated with Endor Labs using GitHub OIDC (keyless) — no token stored Scanning PR 58 (differential vs. main) New findings introduced by this PR: 1 Run succeeded in 1m 47s

Within a minute, the Endor Labs GitHub App posts the scan comment on PR #58:

# PR comment posted by the Endor Labs GitHub App Endor Labs PR scan This PR introduces 1 new finding: [HIGH] CVE-2022-42003 — jackson-databind 2.13.2 — REACHABLE Call path: OrderController.createOrder() -> ObjectMapper.readValue() -> ... Fix: upgrade jackson-databind to 2.13.4.2 No policy violations — this PR is clear to merge.

  • ✓ Confirmed keyless OIDC authentication in the run logs

5

Fail Conditions That Mean Something

The scan's exit code is driven by your Endor Labs finding policies, not by ad-hoc flags in YAML. In the dashboard, open Policies → Finding policies and set the action for reachable criticals to fail the pipeline. Scope it to findings introduced by the PR, so pre-existing debt does not break every branch:

# Finding policy (dashboard) Name: Fail pipeline on reachable criticals Scope: findings introduced by the PR (differential vs. baseline) Match: severity = critical AND reachability = reachable Action: fail the pipeline (endorctl exits non-zero)

Now watch a PR that reintroduces Log4Shell:

# GitHub Actions log, job endor-scan $ endorctl scan --output sarif Scanning PR 61 (differential vs. main) New findings introduced by this PR: 1 [CRITICAL] CVE-2021-44228 — log4j-core 2.14.1 — REACHABLE Policy violations: 1 (fail pipeline on reachable critical) exit status 1

Finish the gate in GitHub: Settings → Branches → Add rule for main, enable Require status checks to pass before merging, and select endor-scan as a required check.

Heads up Fail on introduced findings first. Failing every build on all historical debt creates pressure to disable the gate entirely — the opposite of what you want. Tighten the scope gradually as the backlog shrinks.
  • ✓ Created the fail-on-reachable-criticals policy scoped to introduced findings
  • ✓ Saw the scan exit non-zero on a violating PR
  • ✓ Added endor-scan as a required status check on main

Nightly Full Scans and a Fresh Baseline

PR scans are differential and fast — perfect for the merge gate. But reachability and dependency data need a periodic full pass to stay honest. Add a scheduled job to the same workflow:

# Nightly full scan of main on: schedule: - cron: '0 3 * * *' workflow_dispatch:
$ gh workflow run "Endor Labs Scan" --ref main $ gh run watch Nightly full scan of main Resolving dependencies... done (47 direct, 183 total) Analyzing reachability... done Findings: 27 (3 reachable) Baseline updated: 2026-11-05 03:00 UTC
The full picture A PR gate stops new reachable criticals; the nightly full scan keeps the baseline, reachability, and dependency data current; automated PRs from Endor Labs can propose dependency upgrades so the backlog shrinks without anyone triaging CVE lists by hand.
  • ✓ Added the scheduled full scan to the workflow
  • ✓ Verified the baseline updates after the nightly run
  • ✓ Noted where automated upgrade PRs would come from

🧠 Knowledge Check

Which GitHub Actions permission enables keyless OIDC authentication?
  • permissions: contents: write
  • permissions: id-token: write
  • permissions: security-events: write
  • permissions: pull-requests: write
Why is keyless OIDC preferred over storing an ENDOR_TOKEN secret?
  • It makes scans run faster
  • It avoids needing the GitHub App
  • The runner exchanges a short-lived OIDC token for access — nothing long-lived is stored, so nothing can leak or go stale
  • It is required for SARIF output
Who posts the PR scan comment on a pull request?
  • A custom bot step in your workflow using secrets.GITHUB_TOKEN
  • The Endor Labs GitHub App via the SCM integration
  • GitHub code scanning, automatically
  • A GitHub Actions maintainer account you create
How do you make the scan step fail a pull request?
  • Add continue-on-error: false to the checkout step
  • Set a branch protection rule only — no scan configuration needed
  • Configure a finding policy to fail the pipeline on matching findings — endorctl exits non-zero and the required status check blocks the merge
  • Upload the SARIF file with a failing annotation
