SBOM & VEX Export

Challenge
🕓 30 min 🏆 100 XP 🔄 Compliance 📚 5 steps

🎯 Lab Objectives

  • Generate a CycloneDX SBOM from your latest scan results
  • Generate the SPDX SBOM the auditor also asked for
  • Attach VEX statements backed by reachability analysis
  • Verify the exports meet the audit requirements
  • Package and deliver the evidence for the compliance audit
1

Generate the CycloneDX SBOM

Challenge scenario: the auditor needs an SBOM and a VEX document for checkout-service v1.4.2 by end of day — and only findings your code can actually reach may be claimed exploitable. You have the reachability data; now export it.

Generate the CycloneDX SBOM from the latest scan results:

# CycloneDX SBOM from the latest scan endorctl sbom --format cyclonedx --output sbom.cdx.json
$ endorctl sbom --format cyclonedx --output sbom.cdx.json Generating SBOM from latest scan results... Project: checkout-service 1.4.2 Format: CycloneDX 1.5 Components: 183 (47 direct, 136 transitive) Vulnerabilities documented: 27 SBOM written to sbom.cdx.json (41.8 KB) $ jq '.components | length' sbom.cdx.json 183
Tip The SBOM reflects the scan results, so it carries everything the scanner knows: every dependency, every version, every vulnerability. Export flags and formats evolve — the current syntax lives at docs.endorlabs.com.
  • ✓ Generated the CycloneDX SBOM
  • ✓ Verified the component count (183) matches the scan
2

Generate the SPDX SBOM

The auditor wants both formats. CycloneDX is the security-rich format (it carries vulnerability data and VEX); SPDX is the licensing and compliance standard many procurement processes expect. Endor Labs supports both, plus VEX import and export.

# SPDX SBOM from the same scan results endorctl sbom --format spdx --output sbom.spdx.json
$ endorctl sbom --format spdx --output sbom.spdx.json Generating SBOM from latest scan results... Format: SPDX 2.3 (JSON) Components: 183 License information included for 179 components SBOM written to sbom.spdx.json (58.6 KB)
Why two formats Security teams tend to live in CycloneDX; procurement and legal tend to live in SPDX. Generating both from the same scan means they can never disagree with each other.
  • ✓ Generated the SPDX SBOM
  • ✓ Confirmed both documents describe the same 183 components
3

Attach VEX with Reachability Context

Here is the challenge's twist: a raw SBOM documents 27 vulnerabilities, but the auditor wants to know which are exploitable. A VEX (Vulnerability Exploitability eXchange) document answers that per vulnerability — and Endor Labs generates it from reachability analysis, so every statement is backed by a call path.

# VEX statements generated from reachability analysis endorctl sbom --format cyclonedx --vex --output checkout-service-1.4.2-vex.cdx.json
$ endorctl sbom --format cyclonedx --vex --output checkout-service-1.4.2-vex.cdx.json Generating VEX statements from reachability analysis... exploitable: 3 (reachable call paths) not_affected: 23 (no reachable call path) in_triage: 1 (unknown reachability — jackson-databind) VEX document written to checkout-service-1.4.2-vex.cdx.json

Each statement carries a status and a machine-readable justification:

# From checkout-service-1.4.2-vex.cdx.json { "bom-ref": "pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1", "vulnerability": "CVE-2021-44228", "status": "exploitable", "justification": "Reachable call path: POST /api/orders -> OrderController.createOrder() -> Logger.error() -> JndiLookup.lookup()" } { "bom-ref": "pkg:maven/org.springframework/spring-webmvc@5.3.16", "vulnerability": "CVE-2022-22965", "status": "not_affected", "justification": "No reachable call path from application code to the vulnerable data-binding code" }
Why auditors care The VEX document is the evidence that turns 27 audit line-items into 3. "Not affected, and here is why" is a defensible, reviewable claim — not an assurance or a shrug.
  • ✓ Generated the VEX document from reachability data
  • ✓ Read the exploitable and not_affected statements and their justifications
4

Verify the Exports (Challenge Checks)

Before anything goes to the auditor, prove it is complete. Three checks:

  1. Every one of the 27 vulnerabilities carries a VEX statement
  2. Find the single in_triage item and explain why it is honest
  3. The counts match the dashboard's findings view
$ jq '.vulnerabilities | length' checkout-service-1.4.2-vex.cdx.json 27 $ jq -r '.vulnerabilities[] | select(.status=="in_triage") | .vulnerability' checkout-service-1.4.2-vex.cdx.json CVE-2020-36518 $ jq -r '.vulnerabilities[] | .status' checkout-service-1.4.2-vex.cdx.json | sort | uniq -c 23 not_affected 3 exploitable 1 in_triage

The in_triage item is jackson-databind's CVE-2020-36518, whose reachability is still Unknown pending version confirmation. A VEX document that marks it not_affected would be a lie; in_triage documents the uncertainty honestly — and tells the auditor exactly what you are doing about it.

  • ✓ Confirmed all 27 vulnerabilities have VEX statements
  • ✓ Located the in_triage item and understood why it is not marked not_affected
  • ✓ Matched the 3 / 23 / 1 counts against the dashboard
5

Package It for the Audit

Attach all three artifacts to the v1.4.2 release so the evidence is versioned with the software it describes:

# Attach the evidence to the GitHub release gh release create v1.4.2 \ sbom.cdx.json sbom.spdx.json checkout-service-1.4.2-vex.cdx.json \ --title "checkout-service v1.4.2" \ --notes "SBOM (CycloneDX + SPDX) and VEX with reachability context"
$ gh release create v1.4.2 sbom.cdx.json sbom.spdx.json checkout-service-1.4.2-vex.cdx.json --title "checkout-service v1.4.2" https://github.com/acme-financial/checkout-service/releases/tag/v1.4.2 Artifacts: sbom.cdx.json, sbom.spdx.json, checkout-service-1.4.2-vex.cdx.json

For continuous evidence, Endor Labs integrations can push SBOMs and VEX automatically to Vanta, Wiz, or S3 as each release ships, so audit answers stay current instead of becoming a quarterly scramble. Frameworks like the EU Cyber Resilience Act and US Executive Order 14028 are why auditors ask for SBOMs in the first place — reachability-backed VEX is how you answer them without over-claiming.

Challenge wrap-up You delivered in under 30 minutes: two SBOM formats from one scan, a VEX document where every "not affected" is backed by a call-path analysis, and one honest in_triage flag. That is a defensible audit posture.
  • ✓ Created the release with all three artifacts attached
  • ✓ Noted where automated SBOM/VEX pushes would go (Vanta, Wiz, or S3)
  • ✓ Confirmed every exploitability claim is backed by reachability data

🧠 Knowledge Check

Which two SBOM formats does Endor Labs generate?
  • SPDX and SWID
  • CycloneDX and SPDX
  • CycloneDX and OSV
  • SWID and CSV
What is the correct VEX status for a vulnerability with no reachable call path from your code?
  • exploitable
  • not_affected
  • in_triage
  • fixed
What does a VEX document add to a raw SBOM?
  • License obligations for each component
  • Build timestamps and tool versions
  • Per-vulnerability exploitability status with justifications, backed by reachability analysis
  • The dependency tree structure
Why does the VEX document mark CVE-2020-36518 in_triage instead of not_affected?
  • The CVE has no CVSS score
  • It was already fixed by an Endor Patch
  • Its reachability is Unknown pending version confirmation — the document records the uncertainty honestly
  • The auditor explicitly requested that status
