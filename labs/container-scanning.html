Container Image Scanning

Guided
🕓 40 min 🏆 100 XP 🔄 Containers 📚 5 steps

🎯 Lab Objectives

  • Build a container image for the sample application
  • Scan the image with endorctl container scan
  • Understand reachability from source code into the image
  • Apply base image remediation and use incremental scanning
  • Gate images in the pipeline before they reach a registry
1

Build the Image

checkout-service ships as a container image built from a simple Dockerfile on top of a Java runtime base image. Build the app, then the image:

# Dockerfile FROM eclipse-temurin:17-jre COPY target/checkout-service-1.4.2.jar /app/app.jar ENTRYPOINT ["java", "-jar", "/app/app.jar"]
# Build the app, then the image mvn -q -DskipTests package docker build -t ghcr.io/acme/checkout-service:1.4.2 .
$ mvn -q -DskipTests package BUILD SUCCESS — target/checkout-service-1.4.2.jar $ docker build -t ghcr.io/acme/checkout-service:1.4.2 . [+] Building 4.2s (8/8) FINISHED => [1/2] FROM docker.io/library/eclipse-temurin:17-jre => [2/2] COPY target/checkout-service-1.4.2.jar /app/app.jar Successfully tagged ghcr.io/acme/checkout-service:1.4.2
Tip In production you would pin the base image by digest so builds are reproducible. In this lab the floating tag is deliberate — it is about to teach us something about base image drift.
  • ✓ Built checkout-service-1.4.2.jar
  • ✓ Built and tagged ghcr.io/acme/checkout-service:1.4.2
2

Scan the Image

Endor Labs container scanning analyzes every image layer: OS packages from the base, language packages from your app, and the correlation between the two. Run it against the local image:

# Scan the container image endorctl container scan ghcr.io/acme/checkout-service:1.4.2
$ endorctl container scan ghcr.io/acme/checkout-service:1.4.2 Loading image... done (11 layers) Analyzing OS packages... done (214 packages, debian bullseye) Analyzing language packages... done (87 from app jar) Correlating image contents with source code... done Analyzing reachability... done Findings summary Critical: 4 (1 reachable from app code) High: 9 (1 reachable from app code) Medium: 14 (0 reachable) Low: 6 (0 reachable) From base image (eclipse-temurin:17-jre): 26 findings From application dependencies: 7 findings Results uploaded to Endor Labs: https://app.endorlabs.com/acme-financial/container-images/checkout-service:1.4.2
Notice 33 findings, and the scan tells you where each one lives: 26 come from the base image, 7 from your application's dependencies. That split is your remediation plan — the two need completely different fixes.
  • ✓ Scanned the image and reviewed the summary
  • ✓ Noted the base-image vs. application-dependency split
  • ✓ Opened the image findings in the dashboard
3

Reachability from Code to Image

This is what separates Endor Labs container scanning from a flat CVE list: reachability analysis extends from your source code into the image. You know which of the 33 image findings your application actually executes.

Open the CVE-2021-44228 finding on the image and read the call path:

# Call path — CVE-2021-44228, inside the image Entry point: POST /api/orders (served by app.jar in the image) 1. OrderController.createOrder() [your code, in image] 2. OrderService.validatePayment() [your code, in image] 3. Logger.error(paymentCtx) [log4j-api, in image] 4. JndiLookup.lookup() [log4j-core 2.14.1, in image] * vulnerable function

The same reachable Log4Shell path from the source scan — now proven inside the shipped image. Compare with CVE-2023-0286 in openssl from the base image: present in the image, but no path from application code calls the vulnerable function. It is still worth patching via a base update, but it is not exploitable through checkout-service today.

How the scanning works Endor Labs container scanning is incremental — re-scans analyze only changed layers, so iteration is fast. It also leaves zero cluster footprint: nothing is deployed into your Kubernetes cluster, and registry scanning covers third-party images (like that Postgres you pulled) as well.
  • ✓ Traced the Log4Shell call path into the image layers
  • ✓ Confirmed the base-image openssl CVE is unreachable through app code
4

Base Image Remediation

Open one of the base-image findings in the dashboard — for example CVE-2023-0286 in openssl. The remediation panel shows the base image has been rebuilt upstream with the patched library. Pull the refreshed base and rebuild:

# Pull the updated base image and rebuild docker pull eclipse-temurin:17-jre docker build --pull -t ghcr.io/acme/checkout-service:1.4.3 .
$ endorctl container scan ghcr.io/acme/checkout-service:1.4.3 Loading image... done (11 layers) Incremental analysis: 2 changed layers, re-analyzing... base layer updated: openssl 1.1.1n -> 1.1.1v [-11 findings] Findings summary Critical: 3 (1 reachable — log4j, fix in app code) High: 2 (1 reachable) Incremental scan finished in 41s
Tip One base-image rebuild removed 11 findings — this is the highest-leverage container fix there is. For application-level Java and Python libraries you cannot upgrade outright, Endor Patches provides backported security fixes instead of forcing a major version bump.
  • ✓ Rebuilt the image on the refreshed base
  • ✓ Confirmed the incremental re-scan cleared the openssl findings in 41 seconds
  • ✓ Noted the remaining reachable finding lives in app code, not the base
5

Gate Images in the Pipeline

Scanning on your laptop is a check; scanning in the pipeline is a gate. Add a container scan step that runs before the image is pushed to the registry, so a vulnerable image never becomes pullable:

# CI step (example: GitHub Actions) — scan before push - name: Scan image before push run: | endorctl container scan ghcr.io/acme/checkout-service:${{ github.sha }}
# Pull request that reintroduces a reachable critical: $ endorctl container scan ghcr.io/acme/checkout-service:pr-58 Loading image... done Analyzing packages... done Analyzing reachability... done Critical: 1 (1 reachable from app code) 1 policy violation: reachable critical in image (CVE-2021-44228) exit status 1 # Pipeline fails, image is never pushed to the registry.
Recap Endor Labs container scanning gives you: reachability from code to image (what your app actually calls), incremental speed (changed layers only), base image remediation guidance, registry scanning for third-party images — all with zero cluster footprint.
  • ✓ Added a container scan step before the registry push
  • ✓ Saw the scan exit non-zero on a reachable critical policy violation
  • ✓ Confirmed the image never reached the registry on failure

🧠 Knowledge Check

Which command scans a container image?
  • endorctl scan --image <image>
  • endorctl container scan <image>
  • endorctl image scan <image>
  • endorctl docker <image>
What does "reachability from code to image" tell you?
  • Which container registry the image came from
  • How many layers the image has
  • Which vulnerabilities in the image your application code actually calls
  • Whether the image runs in Kubernetes or Docker
26 findings come from the base image. What is the fastest way to clear most of them?
  • Patch each library inside the running container
  • Rebuild on the updated base image
  • Disable OS-package analysis in the scan
  • Dismiss them as unreachable and move on
What does incremental container scanning mean?
  • Only critical findings are analyzed
  • Only changed image layers are re-analyzed on re-scan, making iteration fast
  • Scans run only when the container is deployed
  • The scan skips base images you have scanned before
