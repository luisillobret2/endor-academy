Why CVSS Alone Is Not Enough

CVSS scores measure the intrinsic severity of a vulnerability — how bad the impact could be if it is exploited. They say nothing about whether the vulnerability is likely to be exploited, whether your application is exposed to it, or whether a fix exists. Sorting a backlog by CVSS alone produces exactly the noise problem reachability solves: hundreds of “critical” findings, most of which will never be triggered in your code.

Mature prioritization stacks multiple signals, each answering a different question:

  • Severity (CVSS) — how bad could it be?
  • Exploitation likelihood — EPSS-style models estimate the probability that a CVE is actually exploited in the wild; a severity-9.8 bug nobody exploits is less urgent than a severity-7.5 bug under active attack
  • Exposure (reachability) — can my application actually trigger this? Only Endor Labs answers this at function level for your specific codebase
  • Actionability — is there a fixed version, a patch, or a healthier alternative package?

💡 The Triage Funnel

Prioritization is a funnel: start with every finding, filter to reachable ones, then rank by severity and exploitation likelihood, then prefer the ones with a fix available. Each layer removes work that does not need to happen. Reachability is the filter no other signal can replicate — and it is the one Endor Labs is known for.

Endor Scores: Package Health Signals

Endor Scores assign each package a risk score built from four families of signals, so you can judge the dependency itself — not just the CVE of the week:

⏰

Activity

Is the project actively maintained? Are issues and pull requests being addressed, and did anything ship recently?

📉

Popularity

How widely is the package adopted? Broad usage signals a healthy community and faster awareness of new issues.

🛡️

Security

What is the package’s vulnerability history and overall security posture, both historically and right now?

🛠️

Code Quality

How well-engineered is the codebase? Quality predicts how quickly maintainers can ship correct fixes.

Endor Scores are used two ways. First, for prioritization: a reachable finding in an abandoned, low-quality package deserves more urgency than the same finding in a healthy one — the healthy package will ship a fix, the abandoned one may never. Second, for dependency selection: before adding a new package, teams compare Endor Scores to choose healthy, actively maintained options and to identify abandoned dependencies worth replacing.

💡 Dependency Selection in Action

Two libraries do the same job. One was last updated three years ago, has open issues with no maintainer response, and a history of CVEs. The other releases monthly, responds to reports, and has a clean security record. Endor Scores make that comparison a glance instead of an afternoon of research — and prevent tomorrow’s findings by choosing better dependencies today.

Combining Reachability and Scores for Triage

Signals multiply their value when used together. A practical triage routine for a customer’s backlog looks like this:

  1. Start with reachable findings — these are the vulnerabilities the customer’s code can actually trigger; everything else stays out of the backlog
  2. Rank by severity and exploitation likelihood — within the reachable set, work critical and actively exploited issues first
  3. Weigh the package’s Endor Score — an unhealthy, abandoned package raises urgency and may justify replacing the dependency rather than upgrading it
  4. Check actionability — prefer findings with a fixed version or an Endor Patch available (Module 05); use upgrade impact analysis to see what a fix touches
  5. Schedule and verify — assign owners, set dates, and confirm fixes with PR scans before merge

⚠️ Important for Partners: Scores Refine, Reachability Decides

Never let scores override reachability. An unreachable CVE in a terrible package is still not urgent; a reachable CVE in an excellent package is still a real problem. The correct story: reachability decides what enters the backlog; Endor Scores and severity decide the order you work it. Astronomer, an Endor Labs customer, described the experience as “noise canceling headphones” for vulnerability management — a phrase worth borrowing in customer conversations.
