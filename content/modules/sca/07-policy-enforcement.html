Policy Types in Endor Labs

Policies turn an organization’s risk appetite into automated decisions. Endor Labs provides four policy families, each enforcing a different part of the program:

Policy Family What It Governs Example
Finding policies What counts as an unacceptable finding — covering OSS vulnerabilities, licenses, SAST, secrets, containers, RSPM, and GitHub Action findings Block critical, reachable OSS vulnerabilities
Exception policies How risk is formally accepted, with templates and expiry dates Time-boxed exception for an unreachable CVE
Remediation policies How quickly findings must be fixed by severity Critical findings resolved within 7 days
Action policies Automated responses when findings or exceptions match rules Notify the owner and open a ticket

💡 Scope Policies to Reality

The strongest finding policies combine criteria — severity, reachability, fix availability — so enforcement targets what is real. A policy that blocks any CVE in the tree recreates the noise problem inside CI and turns developers against the program. A policy that blocks reachable, critical CVEs is something every rational engineer supports.

Enforcing Policies in Pull Requests

Enforcement happens where developers already work. Endor Labs PR scans run in CI integrations such as GitHub Actions, Jenkins, GitLab, and Azure DevOps; every pull request is scanned, and findings surface directly as PR comments — with reachability status and fix guidance, so the developer sees what changed and what to do about it. When a policy is violated, the check fails and the PR is blocked until the finding is fixed or an exception is approved.

  1. Define the policy — set criteria in the Endor Labs platform (severity, reachability, license, fix availability) and scope it to projects or the organization
  2. Start in observation mode — run PR scans that comment but do not block, so teams see what would have failed
  3. Tune with data — adjust thresholds based on what the observation period revealed; this is where reachability earns trust by keeping the blocked set small
  4. Switch to blocking — enable enforcement so new risk cannot merge; existing debt is handled through remediation policies and exceptions
  5. Review exceptions — track accepted risks, expirations, and justifications as part of normal governance

💡 Why the Observe-First Rollout Works

Blocking on day one, before teams trust the findings, generates friction and appeals. Observing first proves the precision — developers see the tool block only reachable, material issues — so by the time enforcement starts, the checks are treated as legitimate. Partners should always recommend this sequencing.

Governance Across the Organization

Policy only scales when it maps to how the company actually operates. Endor Labs governance building blocks:

  • Namespaces — organize projects to mirror the org structure, so policies, ownership, and visibility follow business units and teams
  • RBAC — role-based access control ensures developers see their projects, security teams see the program, and executives see the trends
  • SSO — SAML and OIDC single sign-on with providers such as Okta and Microsoft Entra ID
  • Audit trail — every policy change, exception approval, and enforcement action is recorded — the evidence auditors and assessors ask for

⚠️ Important for Partners: Sell Governance, Not Gatekeeping

CISOs do not buy more roadblocks — they buy control and evidence. Frame Endor Labs policy enforcement as the mechanism that makes security decisions consistent, visible, and defensible: rules defined centrally, enforced automatically in every PR, exceptions documented with expiry, and an audit trail to show for it. That framing, plus reachability keeping blocked sets small, wins the governance conversation.
