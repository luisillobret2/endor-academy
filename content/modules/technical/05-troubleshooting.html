Triage Discipline: The First Five Checks

Most field issues resolve in the first five minutes if you check the same five things in the same order. Work the list before you theorize, and record the answer for each check — the notes become the support ticket if escalation is needed.

  1. Authentication — is the token or key valid, unexpired, and scoped to the namespace holding the project?
  2. Reachability from the runner — can the build agent reach the platform endpoints, directly or through the configured proxy?
  3. Artifact resolution — do private registry credentials resolve every dependency, including git-based ones?
  4. Scan profile — does the profile cover the scan types and paths the customer expects, or did toolchain detection create something narrower?
  5. Scope — is the scan pointed at the repository root rather than a subdirectory, and is the working directory what you think it is?

💡 Pro Tip

Reproduce with the smallest possible scan before escalating. A single-repository scan that fails deterministically is worth more than a dozen reports from a monorepo that fails intermittently. Capture the exact command, the working directory, and the exit code.

endorctl Exit Codes & CLI Diagnostics

In a policy-gated pipeline, a non-zero exit code is often the product working as designed. Endor Labs documents endorctl exit codes so you can distinguish a policy violation from an authentication, resolution, or connectivity failure. Read the documented table before assuming a bug.

  • Success — the scan completed with no gating violations; confirm findings landed in the project.
  • Policy violation — the scan succeeded and a gating policy blocked the build. This is the intended gate, not an outage.
  • Authentication — token invalid, expired, or scoped to the wrong namespace. Re-activate the token or switch to keyless OIDC.
  • Resolution / scan — dependencies or build inputs could not be resolved. Check registry credentials, proxies, and manifest paths.
  • Usage / configuration — bad flag, missing path, or malformed scanprofile.yaml. Re-run with --help and validate the profile file.
# Confirm version and authentication context before deeper debugging
endorctl --version
endorctl activate-token --token "$ENDOR_API_KEY"

# Re-run the failing scan exactly as CI does, from the repository root
endorctl scan --path .

# Always confirm current flags and exit-code behaviour against the docs
endorctl scan --help

⚠️ Important for Partners

Never tell a customer to disable a policy gate to make a red pipeline green. If a gate blocks unexpectedly, review the policy and the finding together. Suppressing the gate hides the exact signal the platform was bought to deliver.

Network, Proxy & Firewall Rules

Connectivity problems look like product problems. Customers behind restricted egress need explicit allow rules, and Endor Labs publishes the firewall and proxy requirements to make that review fast.

  • Egress allow list — apply the published firewall and proxy rules for the endpoints endorctl and the platform components require. Restricting egress too aggressively breaks dependency resolution before it breaks scanning.
  • Proxy configuration — set the proxy variables the CLI honours, and configure Endor Outpost with the same proxy path so both sides of the connection agree.
  • TLS inspection — if the customer terminates TLS inline, confirm the internal CA is trusted by the runner and by the container image used in CI.
  • Outpost placement — deploy Outpost in a subnet that can reach the platform endpoints and the customer’s registries, then verify with a single scoped scan.

Ask the network team for one reproducible test: a single repository scan from the exact runner that fails. Ambiguous reports such as “the scanner does not work” cost days; a failing command with an exit code costs minutes.

Scan Profiles, Scoping, API Key Hygiene & Escalation

Configuration drift, not defects, causes most remaining issues. Two habits prevent it: keep profiles and policies in version control, and treat API keys as credentials with an owner and an expiry.

Symptom, Cause, Fix

Symptom Likely cause Fix
Scan finds far fewer dependencies than the build uses Private registry or git-based dependencies are not resolving Add registry credentials or mTLS, then re-scan and compare counts
No SAST or secrets findings at all Profile created by toolchain detection does not include those scan types Extend scanprofile.yaml and re-run the scan
Pipeline fails intermittently on the scan step Timeout on a large monorepo, or proxy rules dropping long connections Scope the scan, raise the job timeout, and confirm proxy idle limits
Automation stops working without any change API key rotated, expired, or scoped to a different namespace Re-issue a namespace-scoped key and update the CI secret
Reachability verdicts look thin Approximate or binary artifact scan used where source was available Scan from source with a full profile to build the call graph

When to Escalate to Endor Labs Support

Escalate once the five triage checks are done and the issue reproduces with a minimal command. Include the endorctl version, the exact command and working directory, the exit code, sanitized scan output, the affected namespace and project, and the business impact. Never send API keys, secrets, or customer source in a ticket.

💡 Pro Tip

Rotate keys on a calendar, not on an incident. A quarterly rotation tied to the customer’s own change process turns key hygiene into a non-event instead of a pipeline outage.
