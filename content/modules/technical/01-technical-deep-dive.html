Platform Architecture: SaaS Control Plane + Endor Outpost

Endor Labs is an Agentic Application Security Platform: a SaaS control plane at app.endorlabs.com that scans code, dependencies, containers, secrets, and AI assets, then drives triage and remediation. Two architectural facts decide most enterprise conversations — the platform is SaaS-first, and Endor Outpost is the customer-controlled component that makes it viable where egress is restricted.

Component Reference

Component Purpose Deployment note
Endor Labs SaaS Scan orchestration, findings, policies, dashboards, API Hosted by Endor Labs at app.endorlabs.com, reached over HTTPS
Endor Outpost Customer-controlled deployment component for restricted-egress environments Runs inside the customer network and supports proxy configuration
Namespaces & RBAC Organize projects and organizations; scope access and reporting Map one namespace per business unit; federate users via SAML/OIDC (Okta, Entra ID)

Lead architecture calls with the Outpost question: “Can your build runners reach the public internet directly?” If the answer is no, proxy rules and Outpost placement become the design, and everything else is configuration detail.

Authentication, Identity & Access Control

Three authentication paths cover almost every requirement. Start with the one that matches the customer’s constraint, then show how they combine.

  • SSO (SAML / OIDC) — federate human users through Okta, Entra ID, or any SAML/OIDC provider; group mappings drive authorization roles.
  • Keyless OIDC — CI workloads on GitHub, AWS, Azure, and Google Cloud authenticate with no long-lived secrets. Preferred in regulated pipelines.
  • API keys — for automation that cannot use OIDC; scope each key to the minimum namespace and rotate on a schedule.

Bootstrap a Scan in Four Steps

  1. Install endorctl — use the packaged installer for the OS, or the container image on a CI runner.
  2. Activate the token — run endorctl activate-token --token <API_KEY>; in CI, prefer keyless OIDC instead of a stored key.
  3. Scan the repository — run endorctl scan --path .; toolchain detection creates a scan profile for the languages it finds.
  4. Confirm findings — results land in the namespace the token was scoped to; verify the project in app.endorlabs.com.

⚠️ Important for Partners

Never place a personal API key in a customer pipeline. Create a dedicated service key scoped to one namespace, store it in the customer’s secret manager, and rotate it on their schedule. Exact CLI flags change between releases — confirm with endorctl scan --help before publishing a runbook.

Scan Methods, Profiles & Toolchain Detection

There is no single correct way to scan. Match the method to where the code already lives and where the customer will accept a gate.

Method Where it runs Best for
SCM apps GitHub, GitLab, Bitbucket Cloud Fast onboarding with PR comments and PR blocking
CI/CD integrations GitHub Actions, Jenkins (including supervisory scans), GitLab, Azure DevOps, Bitbucket, CircleCI, Google Cloud Build, Buildkite Build-time gates inside pipelines the customer already owns
endorctl CLI Developer laptop, container, any runner Ad-hoc scans, custom automation, constrained networks

Scan profiles define what runs. Configure them in the UI, through the API, or as code in scanprofile.yaml, and let toolchain detection create profiles automatically for each discovered language. Scan types include SCA, SAST (rule-based plus AI SAST), secrets, containers, malware, AI models, OSS licenses, RSPM for GitHub misconfigurations, and PR scans. Reachability comes from call graph construction, with pre-computed reachability available for faster triage. Binary artifact scans and approximate scans cover code without buildable sources, and Bazel (via Aspects) plus monorepos are first-class. Language coverage spans 40+ languages, including Java, Python, Go, JavaScript/TypeScript, C/C++, PHP, Kotlin, Scala, .NET, Swift/Objective-C, Ruby, and Rust.

Findings Pipeline, Policies & Remediation

A finding only matters if it reaches the person who can fix it. The Endor Labs pipeline covers triage, policy, routing, and repair.

  1. Find — scans produce findings that can be filtered by severity, reachability, package, project, and scan type.
  2. Triage — dismiss findings with a recorded reason, or attach exception policies created from templates so decisions stay auditable.
  3. Enforce — finding policies cover container, license, RSPM, OSS, SAST, secret, and GitHub Action findings; remediation and action policies automate the response.
  4. Route — PR scans comment inline and can block a pull request; notifications and integrations push the rest to Jira, Slack, email, and webhooks.
  5. Fix — upgrade impact analysis and automated pull requests handle version bumps; Endor Patches backport fixes for Java and Python via Patch Factory.
  • Dashboards & reports — OSS overview, Endor Patches, first-party code, analytics, AI security code review, and OSS coverage views, plus scan history and scheduled reports.
  • SBOM & VEX — export CycloneDX or SPDX SBOMs with VEX statements, and import SBOMs to enrich inventory for compliance work.
  • Package Firewall — blocks malicious packages at install time for agents and developers, closing the window between publish and patch.
  • AURI agent stack — inventories agents, models, MCP servers, and skills, and applies allow, block, or ask-a-human decisions with an audit trail.

💡 Pro Tip

Anchor the architecture story on outcomes: reachability cuts the queue, PR scans keep it cut, and Endor Patches clear residue that no upgrade can fix. Zebra reports a 97% noise reduction and Egnyte reports 70% faster MTTR — use customer numbers as proof, not as promises.
