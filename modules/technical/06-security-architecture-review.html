Security Architecture Review

🕒 40 min 📚 5 sections ⭐ 200 XP Level 3 - Advanced

🎯 Learning Objectives

In this module you will cover:

  • Threat-Model the Customer’s SDLC
  • Map Controls to the Platform: Scan, Triage, Remediate
  • Finding the Gaps: Agent Governance & Package Firewall
  • Write the Review as a Proposal

Threat-Model the Customer’s SDLC

A security architecture review is not a product presentation. It is a structured threat model of how code travels from a developer’s machine to production, followed by a control map that shows where the platform closes each gap. Run the review with Endor Labs as the lens, but start from the customer’s pipeline, not your feature list.

Walk the pipeline in five stages and ask one question at each: what can go wrong here, and who would notice?

SDLC stage Threat Control in the platform
Author — IDE, agents, local installs A malicious package is pulled at install, or an agent reaches untrusted tooling Package Firewall blocks malicious packages at install; agent, model, and MCP inventory records what agents can reach
Integrate — pull requests New code introduces a reachable vulnerability, a secret, or an insecure workflow PR scans with SAST (rule-based and AI SAST), secrets detection, RSPM for GitHub misconfigurations, and inline PR comments
Build — CI/CD The pipeline itself becomes the weakest link: unenforced gates, unscoped scans CI integrations across GitHub Actions, Jenkins, GitLab, Azure DevOps, CircleCI, Google Cloud Build, and Buildkite with policy gates
Publish — registries and artifacts Vulnerable or unlicensed components ship as first-party releases SCA with reachability, OSS license findings, SBOM and VEX export, and binary artifact scans
Run — containers and production Base images and layers carry known vulnerabilities and malware Container scanning, malware detection, and Endor Patches where no upstream fix exists

💡 Pro Tip

Send a one-page questionnaire before the session: languages, SCM platforms, CI systems, registries, current scanners, and the top three AppSec complaints. Arriving with the pipeline already sketched turns a discovery meeting into a design meeting.

Map Controls to the Platform: Scan, Triage, Remediate

Once the pipeline is on the whiteboard, map every identified gap to one of four control verbs. Keep the mapping explicit — customers approve architectures they can trace.

  1. Scan — connect SCM apps and CI pipelines, or run endorctl directly; define scan profiles in the UI, the API, or scanprofile.yaml, and let toolchain detection create profiles for each language.
  2. Triage — use reachability from call graph construction to separate exploitable findings from theoretical ones, filter the queue, and dismiss findings with a recorded reason.
  3. Remediate — run upgrade impact analysis, open automated pull requests, apply Endor Patches for Java and Python where no upstream release exists, and block malicious installs with Package Firewall.
  4. Prove — export SBOMs and VEX in CycloneDX or SPDX, review OSS coverage and analytics dashboards, and feed compliance platforms such as Vanta with control evidence instead of screenshots.

Express each control in the customer’s language. If the audit team asks for supply-chain transparency, the answer is SBOM and VEX, not “SCA”. If the platform team asks how a dependency gets fixed, the answer is upgrade impact analysis and automated pull requests, not “remediation”.

Finding the Gaps: Agent Governance & Package Firewall

Most reviews find the same two blind spots. Traditional AppSec programs start at the pull request, so anything that happens before a scan — or outside the codebase entirely — is ungoverned.

🛡️

Before the scan: Package Firewall

Malicious packages act at install time, before any dependency scan runs. Package Firewall blocks them at install for both agents and developers, which is the only control that arrives early enough.

🤖

Outside the codebase: agent governance

AURI inventories agents, models, MCP servers, and skills, draws context from files such as AGENTS.md and CLAUDE.md, and applies allow, block, or ask-a-human decisions with an audit trail.

For AI-heavy customers, extend the review into the agent supply chain: which agents exist, which MCP servers they call, which models they reach through AI Model Discovery, and how Agents Hub delegated credentials and trust attribution are managed. The MCP server is available through npx -y endorctl ai-tools mcp-server for Cursor, Claude Code, Codex, VS Code, Gemini CLI, Antigravity, IntelliJ, Devin, OpenCode, and GitHub AgentHQ.

⚠️ Important for Partners

Never present a gap as a failure of the customer’s team. Frame it as scope that no traditional scanner covers: “Your program governs what lands in the repository; nothing currently governs what installs before that, or what your agents can reach.” That framing makes the gap a roadmap item rather than a criticism.

Write the Review as a Proposal

The deliverable is a short document that a champion can forward without editing. Six pages beat sixty: every section must support the recommendation that follows it.

  1. Executive summary — current state, the three highest-risk gaps, and the proposed controls in one page.
  2. Threat model — the pipeline diagram with the five stages and the threats identified in the workshop.
  3. Control map — each threat paired with the platform capability that closes it, plus the integration required to deliver it.
  4. Gap register — open items the platform does not cover today, with the compensating control or roadmap dependency stated plainly.
  5. Phased rollout — pilot scope, repository list, integration order, and named owners on both sides.
  6. Success metrics and commercial alignment — noise reduction, reachable-finding coverage, MTTR, PR scan adoption, and the licensing shape that supports the rollout.

💡 Pro Tip

Attach the review to the POV charter so the report becomes the technical appendix of the proposal. When the readout arrives, the customer is not evaluating a new document — they are confirming one they already helped write.

Knowledge Check

Question 1: In a control-mapping review, which capability separates “this CVE exists in my dependency tree” from “this CVE can actually be exploited”?

Question 2: Which two areas most often appear as gaps because they sit outside the scan-triage-remediate loop?

Question 3: What makes the review document persuasive to an economic buyer?
