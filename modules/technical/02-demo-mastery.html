The 17-Minute Endor Labs Demo Flow

A demo that runs long loses the room. The Endor Labs story fits in 17 minutes because every act ends in a decision, not a feature tour. Run the acts in this order and hold the clock: if the prospect is engaged, deepen an act rather than adding a new one.

Act What you show Time
1. Connect & scan Connect a repository through the SCM app, watch toolchain detection build the scan profile, and open the first findings set 3 min
2. Reachability triage Open a critical finding, show the call path from application code into the vulnerable function, then dismiss an unreachable finding with a reason 5 min
3. Remediation Run upgrade impact analysis, show the automated pull request, then show an Endor Patch where no upstream fix exists 3 min
4. Package Firewall Attempt to install a known-malicious package and let the firewall block it at install time 3 min
5. AI & agents Inventory agents, models, MCP servers, and skills, then show an AI SAST review comment on a pull request 3 min

💡 Pro Tip

Reachability is the act that sells. When a critical CVE is marked unreachable and you can display the call graph evidence behind that verdict, noise-weary teams lean in. Reserve the most time for act 2 and rehearse the call-path narration until it is under a minute.

Demo Environment Setup Checklist

Demo quality is an operations problem, not a talent problem. Maintain one hardened demo organization and treat it like production.

  1. Demo organization — a dedicated namespace with realistic projects across Java, Python, JavaScript/TypeScript, and Go, plus at least one container image and one Bazel or monorepo project.
  2. Pre-scanned repositories — scan everything the night before so findings, call graphs, and dashboards are already populated when the call starts.
  3. Malicious package fixture — a throwaway project that references a known-bad package so the Package Firewall block is repeatable.
  4. Agent and MCP inventory — at least one registered agent, one MCP server, and context files such as AGENTS.md so governance decisions are visible.
  5. Remediation artifacts — a pre-opened pull request and one Endor Patch example, so act 3 never waits on a build.
  6. Fallback captures — screenshots or a short recording of each act in case the network, SSO, or a live scan misbehaves.

Refresh the environment monthly: replace aging CVEs with current ones, re-run scans so timestamps look live, confirm every integration still authenticates, and add newly released capabilities within a week.

⚠️ Important for Partners

Never demo on an unproven network. Ask the customer to confirm screen-share bandwidth and whether outbound HTTPS is filtered on their side. If the customer insists on scanning their own repository live, run a dry scan against a clone beforehand and keep the pre-scanned project as the fallback path.

Tailoring the Story by Audience

The same 17 minutes should feel different to different rooms. Change the framing and the depth, not the product.

📈

CISO / VP Security

Lead with noise reduction, reachable-finding coverage, MTTR, and governance. Show the OSS coverage and analytics dashboards, the agent audit trail, and how exception policies create an evidence trail for audits.

🛠️

VP Engineering / Platform

Lead with developer workflow: PR scans that comment inline and can block, upgrade impact analysis, automated pull requests, and Endor Patches that clear dependencies no upstream release will fix.

🔒

Security Engineering / AppSec

Lead with depth: scan profiles and scanprofile.yaml, policy types, SBOM and VEX export, RSPM for GitHub misconfigurations, and how call graph construction produces reachability verdicts.

Before showing anything, ask one question: “What would make this hour worth your time?” Then cut acts that do not serve that answer. A demo that skips act 4 to spend nine minutes on reachability is a better demo than one that runs every act on schedule.

Common Demo Mistakes & Recovery

  • Feature tour instead of a story — narrate a developer’s day: finding, triage, fix, merge. Never walk a menu.
  • Testing an unreachable CVE — if the flagship finding turns out to be unreachable, you have argued against your own value. Curate findings that are both critical and reachable.
  • Boiling the ocean — scanning the customer’s entire estate live produces an unusable backlog. Scan one representative repository.
  • Ignoring the incumbent — never disparage the tool the room bought. Frame Endor Labs as the consolidation path that removes the noise their current tool generates.
  • No next step — every demo ends with a named action: a scoped POV, a repository list, or an architecture review date.

💡 Pro Tip

Recover in the open. If a scan fails mid-demo, say so, switch to the pre-scanned project, and use it as proof that you plan for failure. Prospects remember composure far longer than they remember a call graph.
