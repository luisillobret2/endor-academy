Ticketing & ChatOps: Jira, Slack, Email, Webhooks

Integrations decide whether findings reach humans. Sequence them by effort and payoff: SCM app first for scanning, Slack or email next for visibility, Jira for ownership, then webhooks for anything bespoke.

  • Jira — create issues for findings that need an owner and an SLA; map reachable critical findings to the highest priority and let exception policies suppress the rest.
  • Slack & email — route notifications to the channel or list that owns the project; use digests for volume and direct alerts only for reachable critical findings.
  • Webhooks — push findings into any internal system; confirm the payload schema against the API docs before writing field mappings into production code.
  • Pull request comments — PR scans comment inline and can block a pull request. This is the integration developers actually read, so enable it early.

Webhook-to-Jira Recipe

Stand up a small receiver, verify the event schema, then map severity to issue type and reachability to priority. Keep the receiver stateless so it can be retried safely.

# 1. Create the webhook in the Endor Labs UI and point it at your receiver
# 2. Validate the payload schema against the Endor Labs API documentation
# 3. Map fields: severity -> issue type, reachability -> priority
# 4. Always return HTTP 200 quickly and process asynchronously

curl -X POST "https://jira.example.com/rest/api/2/issue" \
  -H "Authorization: Bearer $JIRA_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"fields":{"project":{"key":"SEC"},"issuetype":{"name":"Task"}}}'

💡 Pro Tip

Never let a noisy integration undermine a good rollout. Start with notifications only, measure the volume for a week, then add ticketing with reachability-based filters. An integration that files 800 tickets on day one gets switched off by day three.

Data Exporters & Security Platform Feeds

Enterprise security teams want Endor Labs data in the tools they already operate. Exports and feeds remove the manual reporting step from every review cycle.

Target What it gives the customer Notes for the SE
Amazon S3 Scheduled export of findings and inventory into customer-owned storage Preferred when data residency or warehouse analysis matters
GitHub Advanced Security Data exporter that surfaces Endor Labs results alongside GitHub-native findings Useful when developers live entirely in GitHub
Wiz Correlate application findings with cloud and workload context Position as complementary coverage, not overlap
Microsoft Defender for Cloud Feed application risk into the cloud security posture workflow Common requirement in Azure-first enterprises

For audits, pair an export with an SBOM and VEX bundle in CycloneDX or SPDX. The VEX statements explain why specific findings are not exploitable, which is exactly the evidence auditors and compliance platforms such as Vanta ask for.

Private Package Managers & Endor Patches Infrastructure

Enterprises rarely pull dependencies straight from public registries. Endor Labs integrates with private package managers so scans resolve the same artifacts the build actually consumes, including git-based dependencies and registries that require mTLS.

  • Ecosystems — Maven, Gradle, npm, PyPI, NuGet, RubyGems, Swift, Packagist, and Conan.
  • Cloud registries — AWS CodeArtifact and Google Artifact Registry, alongside self-hosted Artifactory and Nexus instances.
  • Authentication — token-based access or mutual TLS (mTLS) for registries that require client certificate authentication.
  • Git-based dependencies — resolve dependencies declared as git references so private forks and pinned commits are scanned like any other package.

Endor Patches Delivery

Endor Patches backport fixes for Java and Python packages when no upstream release exists. Patch Factory produces the patched artifact, and delivery integrates with JFrog Artifactory and Sonatype Nexus so the customer’s build resolves the patched version from their own registry. Patch transparency matters here: every patch is traceable to the advisory it addresses, which is what gets security review approval.

⚠️ Important for Partners

Private registry credentials are the most common cause of an incomplete first scan. Confirm registry access before the POC kickoff, and prefer mTLS or a scoped service account over a personal token. Incomplete resolution silently weakens reachability verdicts.

API Automation & SCM App Management

Everything the UI does is available for automation, which is how large customers avoid manual toil across hundreds of projects.

  1. Manage SCM apps centrally — install the app once per organization for GitHub, GitLab, or Bitbucket Cloud, then add repositories as scan targets rather than installing per repo.
  2. Automate scan profiles — keep scanprofile.yaml in the repository so profile changes are reviewed like code instead of clicked in a UI.
  3. Drive policy as code — create finding, exception, remediation, and action policies through the API so policy sets are versioned and reproducible across namespaces.
  4. Scope keys per namespace — give each business unit an API key limited to its namespace; use keyless OIDC where the CI platform supports it.
  5. Export on a schedule — automate SBOM and findings exports so reporting does not depend on a human remembering.
# Keep profile and policy changes reviewable, and confirm the auth context
endorctl scan --path . --scan-profile ./scanprofile.yaml
endorctl activate-token --token "$ENDOR_API_KEY"

💡 Pro Tip

When a customer asks for a custom integration, ask what decision the integration supports. Most requests resolve to a notification, an export, or a policy gate — three things the platform already does without custom code.
