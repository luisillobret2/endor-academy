Why Alerting on Every CVE Fails Teams

Traditional SCA works like an inventory system with a loudspeaker: it reports every CVE found anywhere in the dependency tree, whether or not your application can trigger it. A large application carries hundreds of direct and transitive packages, so a single scan can produce hundreds or thousands of findings — and studies show that most reported CVEs are never actually invoked by the application.

Consider what happened when Log4Shell (CVE-2021-44228) surfaced in December 2021. Organizations worldwide had log4j somewhere in their dependency trees, but almost none could answer the one question that mattered: does our code actually invoke the vulnerable JNDI lookup path? Teams spent days reading code and holding emergency meetings to find out. Reachability analysis answers that question automatically, every time.

💡 Severity Without Exposure Is Just a Number

A vulnerability only matters to your application if there is a path from your code to the vulnerable function. The question is not “is this CVE in our tree?” but “can this be triggered in our application?” That is exactly the question Endor Labs reachability analysis answers.

The cost of alerting on everything is well documented: security teams burn out triaging noise, developers stop trusting security tooling, emergency response gets diluted across non-issues, and the genuinely exploitable findings get buried. Alert fatigue is not an inconvenience — it is the reason many AppSec programs fail.

How Endor Labs Builds Call Graphs

Endor Labs performs function-level reachability analysis across 40+ languages, including Java, Python, Go, JavaScript/TypeScript, C/C++, PHP, Kotlin, Scala, .NET, Swift/Objective-C, Ruby, and Rust. The engine works through four steps:

  1. Resolve the dependency tree — Endor Labs reads your manifests and lockfiles and resolves every direct and transitive dependency, so nothing in the tree is invisible
  2. Construct the call graph — the analysis maps function calls starting from your first-party code and follows them through dependency code, layer by layer, across transitive dependencies
  3. Map vulnerable functions — each known vulnerability is mapped to the specific functions in the dependency that contain the flaw
  4. Classify each finding — a vulnerability is reachable only if a real call path exists from your code to the vulnerable function; everything else is classified as unreachable

Endor Labs also provides call graph visualization in the product: instead of telling a developer “this CVE is reachable,” the tool shows the exact call path from your code into the vulnerable function. Developers can verify the finding themselves, which is what turns security output into engineering action.

Status Meaning Action
Reachable Your code calls the vulnerable function through a real call path — the vulnerability can plausibly be triggered in your application Prioritize for remediation now
Unreachable No call path from your code reaches the vulnerable function — exploiting it would require your application to change first Kept out of the backlog; handle during normal maintenance

💡 Function-Level, Not Package-Level

“We use that library” is not the right question. Most libraries contain large amounts of code your application never calls. Endor Labs tracks usage down to the individual function inside the dependency, which is why it can safely exclude critical CVEs in packages you depend on — when those CVEs live in functions you never invoke.

Noise Reduction in Practice

The operational change is simple and powerful: only reachable findings enter the backlog. Instead of starting from every CVE in the tree, teams start from the small set of vulnerabilities their code can actually reach. Zebra Technologies, an Endor Labs customer, reported reducing SCA noise by up to 97% after adopting reachability.

Consider a concrete scenario. Your web application uses a popular PDF library — a direct dependency — exclusively for generating quarterly reports. A critical CVE is published in the library’s image-rendering module, a feature your application never touches.

⚠️

Without Reachability

The CVE is critical and the package is in the tree, so the team gets a critical alert. An incident review is scheduled, engineers pull apart the dependency tree, and after several hours they conclude the vulnerable code path is never used. The effort was wasted — and the same cycle repeats with the next CVE.

✓

With Endor Labs Reachability

Endor Labs maps the call graph and finds no path from your code to the image-rendering function. The finding is classified unreachable and never enters the backlog. The library upgrade happens in the next routine maintenance cycle — no incident, no interruption.

Reachability Beyond Libraries: Containers and Pre-Computed Results

Reachability is not limited to library dependencies. Endor Labs container scanning applies reachability from code to image: for a container image that includes your application, Endor Labs can tell you whether an OS or package vulnerability in the image is actually reachable through your application code. Teams stop rebuilding images reflexively over vulnerabilities their code never touches.

Endor Labs also supports pre-computed reachability: reachability results are computed ahead of time, so scans — including pull request scans in CI — return with the reachability verdict already attached. Developers get precise, actionable feedback at pull request speed instead of waiting for deep analysis to finish.
