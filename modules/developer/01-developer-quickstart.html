Security That Does Not Change Your Workflow

Developers adopt security tooling for exactly one reason: it does not move their work. Endor Labs was built around that constraint. The platform runs where you already are — the terminal via endorctl, your editor and coding agents via the MCP server, your pull requests via PR scans, and your pipeline via CI/CD integrations. There is no new portal to visit and no new queue to babysit.

💡 The “No Workflow Change” Promise

One policy applies from laptop to pipeline. You scan the repository you already work in, findings arrive as PR comments or agent suggestions inside the tools you use, and fixes are applied from your editor. Security stops being a separate place you go and becomes part of the code review you already do.

This quickstart takes you from zero to a completed first scan and your first fix — the same path you will walk customers down during a demo. No security expertise is required, and nothing about your repository setup changes.

Set Up: Account, Token, and Repository

Three steps stand between you and your first scan:

  1. Create your account — sign in to the Endor Labs console at app.endorlabs.com. As a partner, use the credentials issued for your academy and partner workspace.
  2. Create an API token — in the console, create a dedicated API token. Treat it like a password: store it in an environment variable, never in source code, and use a separate token for automation so you can revoke it without touching your own access.
  3. Connect your repository — either connect the repository integration in the console, or simply run endorctl inside the repository. The project, its dependency inventory, and its findings are created automatically on your first scan.

⚠️ Important for Partners

The first five minutes decide adoption. When you walk a customer through Endor Labs, do not narrate slides — run these three steps live against a real repository. The quickstart is the demo: account, token, scan, findings, fix.

Install endorctl and Run Your First Scan

endorctl is a single binary for macOS, Linux, and Windows, and is also available as a container image for CI runners. Install it with the packaged installer for your operating system from the Endor Labs docs, then verify and run:

# Verify the installation
endorctl --version

# Authenticate with the token you created in the console
endorctl activate-token --token=$ENDOR_TOKEN

# Scan the repository you are in
endorctl scan

That last command does the heavy lifting. endorctl auto-detects your toolchains across 40+ languages, resolves the full dependency tree from manifests and lockfiles, maps call paths between your code and your dependencies, and uploads the results to your project in the console. Your first scan is a baseline: every dependency, every known vulnerability in them, plus secrets and code findings according to your scan profile.

💡 One Command, Full Inventory

Every endorctl scan resolves direct and transitive dependencies, builds the call graph that powers reachability analysis, and returns prioritized findings in the console within minutes. The scan profile — what to scan and which analyses to run — is auto-detected on first run and can be pinned in a scanprofile.yaml so every teammate and every pipeline scans identically.

Read Your Findings and Fix Your First One

Open your project in the console and you will see findings grouped by risk. The single most important signal is reachability: Endor Labs function-level call graphs tell you whether your code actually calls the vulnerable function in a dependency — the difference between a vulnerability you can exploit and one that just looks scary in a report.

Status What it means What you do
Reachable Your code calls the vulnerable function — this can actually be triggered Fix first; these are the real risks
Potentially Reachable A call path may exist; analysis is inconclusive Investigate and schedule
Unreachable Your code never calls the vulnerable function Deprioritize; update in the normal cycle

Your First Fix

  1. Sort by reachable critical and high findings — start where the risk is real.
  2. Open a finding and read the call path — see exactly how your code reaches the vulnerable function. Evidence beats severity scores.
  3. Apply the suggested fix — take the recommended version upgrade (Endor Labs can raise the update as an automated pull request) or apply an Endor Patch when you cannot upgrade yet.
  4. Re-run endorctl scan — confirm the finding clears. That closes the loop.

Scan, triage by reachability, fix, rescan — that is the entire developer loop with Endor Labs. The rest of this track shows you how to run that loop from your IDE and coding agents, your CI, and your policies.
