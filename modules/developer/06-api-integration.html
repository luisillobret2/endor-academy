One Platform, Fully Automatable

The Endor Labs REST API exposes the same objects the console uses, which is what makes the platform scriptable end to end: you can manage projects, findings, policies, and scan results, and configure scan profiles, from your own tooling. Anything an engineer does by hand in the UI — triage a finding, grant an exception, adjust a policy, review a scan — can be automated, scheduled, and folded into the customer’s existing systems.

That is the partner-relevant point: the API is how Endor Labs lands inside an enterprise instead of alongside it. Customer dashboards, ticketing workflows, compliance evidence, and internal portals all become thin clients over the same data.

Resource What you manage through it
Projects The applications and repositories being scanned — listing, state, and metadata
Findings Vulnerabilities, secrets, license issues, and policy violations — filterable by severity, status, and reachability
Policies Finding, exception, and remediation policies, created and versioned like code
Scan results Individual scan runs and their outcomes, for history and audit
Scan profiles What each scan analyzes — the same profiles endorctl uses, managed centrally

💡 Work From the API Reference

The console itself runs on this API — automation is not a bolt-on. Endor Labs publishes a complete API reference (OpenAPI) documenting every endpoint, parameter, and schema. The examples in this module illustrate the patterns; exact paths and request shapes come from the reference for your tenant, and the reference evolves with the platform.

Authentication: Keys, Service Accounts, and Keyless OIDC

API keys are created in the Endor Labs console and used to obtain short-lived bearer tokens, which travel in the Authorization header on every request. Tokens expire by design — build refresh into your client instead of caching one token forever, and never embed a key in source code: load it from an environment variable or a secrets manager.

For automation, create a dedicated service account with least-privilege scope rather than reusing a human’s key. If a token leaks, you revoke the service account without disrupting a person; and the audit trail clearly attributes automated actions to the integration, not to whoever ran it.

In CI, prefer keyless OIDC authentication — supported for GitHub, AWS, Azure, and GCP — so no secret is ever stored in a pipeline at all. The GitHub Actions lab walks through this end to end.

# Authenticate an API call (illustrative - exact paths and schemas
# are documented in the Endor Labs API reference)
export ENDOR_API="https://api.endorlabs.com"

curl -H "Authorization: Bearer $ENDOR_BEARER_TOKEN" \
  "$ENDOR_API/orgs/$ORG_UUID/projects?pageSize=100"

Two practical rules for any client you write: page through list results to the end (a large project has far more findings than one page), and when the API throttles you, wait and retry instead of hammering — throttling is normal operation, not an error condition.

Webhooks: Push, Don't Poll

Polling finds out about a new critical finding whenever your next scheduled run happens. Webhooks close that gap: you register HTTPS endpoints, and Endor Labs pushes real-time notifications — a scan completing, a new finding, a policy violation — as JSON POSTs the moment the event occurs. Reaction time becomes a design decision, not a cron schedule.

A production receiver follows four rules: verify the request signature exactly as documented for your tenant, respond 2xx quickly, hand heavy work to a background queue, and treat deliveries as repeatable (make handlers idempotent).

# Illustrative webhook receiver: validate, filter, fan out.
from flask import Flask, request, os, requests

app = Flask(__name__)

@app.post("/webhooks/endor")
def receive():
    # Verify the request signature as documented for your tenant
    # before trusting the payload. Field names below are illustrative.
    event = request.get_json()

    if event.get("severity") == "critical" and event.get("status") == "open":
        notify_slack(event)          # alert the owning channel
        create_jira_issue(event)     # land it in the backlog
    return "", 204

def notify_slack(event):
    requests.post(os.environ["SLACK_WEBHOOK_URL"], json={
        "text": f"Critical finding: {event.get('name')}"
    })

def create_jira_issue(event):
    requests.post(
        f"{os.environ['JIRA_URL']}/rest/api/3/issue",
        auth=(os.environ["JIRA_USER"], os.environ["JIRA_TOKEN"]),
        json={"fields": {"project": {"key": "SEC"},
                         "summary": f"Security: {event.get('name')}"}})

Before you write that receiver, check what already exists: Endor Labs ships integrations for Jira, Slack, and email, and connects findings into Vanta for compliance evidence and Microsoft Defender for Cloud for cloud security programs. Custom code should be the last resort, not the first draft.

Data Exporters, Integrations, and Automation Recipes

Data exporters push findings to the customer’s systems of record with no custom code to maintain:

💻

GitHub Advanced Security

Findings surface in the code-scanning view of the repositories developers already watch — security in the tools they have already paid for.

🗃

S3

Findings land in a data lake for historical trends, SLA tracking, and custom BI — no polling job required.

☁

Wiz

Application findings correlate with cloud security posture, so one team sees code risk and cloud risk together.

Six automation recipes partners deploy again and again:

  1. GHAS export — surface reachable critical and high findings in GitHub code scanning
  2. S3 export — keep findings history for trend and remediation-time reporting in your BI tool
  3. Wiz export — correlate application findings with cloud posture in one console
  4. Jira integration — auto-create issues for reachable criticals, assigned to the owning team
  5. Slack alerts — notify the channel that owns the affected service in real time
  6. Scan profiles via API — manage scan configuration as code across every project in the org

And when the automation needs to act rather than report, endorctl closes the loop in any pipeline — GitHub Actions, Jenkins, GitLab, Azure DevOps, Bitbucket, CircleCI, Google Cloud Build, and Buildkite — as covered in the endorctl CLI & Automation module.

⚠️ Important for Partners

Exporters are the “meet the customer where they already are” story: no rip-and-replace, no parallel dashboard. The GHAS exporter is a wedge into GitHub-heavy accounts that have already bought Advanced Security; Vanta and Microsoft Defender for Cloud extend the conversation into compliance and cloud security, where new budget lives.
